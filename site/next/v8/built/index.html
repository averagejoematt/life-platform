How it’s built

What runs, what it costs, and what has broken.

This site is one person’s health data, read by a set of AI coaches whose predictions are graded by code. Matthew is not an engineer. He decided what the system does, set its limits and approves its releases. The code was written with an AI assistant, Claude.

What runs

One picture.

A change to program code reaches the running parts only after the checks and the approval. Page files are the exception, covered below.

The numbers

Counted, with dates.

Cost

A ceiling, and what switches off.

A program forecasts the month-end bill every 8 hours and sets a tier from it. Each AI feature reads the tier before it runs.

  • Tier 0Everything runs.
  • Tier 1From about 73% of the ceiling. Three internal AI passes stop. Nothing a reader sees changes.
  • Tier 2From about 87%. The coaches’ daily commentary, the weekly brief, the weekly chronicle and the podcast stop.
  • Tier 3From about 97%. All AI stops. A reader’s question gets a “paused” answer and the daily email goes out with data only.

A forecast alone can raise the tier by one step at most, and by none in the first 5 days of a month. The stricter tiers need money actually spent.

Who decides

What a person approves.

  • LimitsThe monthly ceiling and the order in which features pause were decided in advance and written into code.
  • ApprovalThe release pipeline stops for Matthew’s approval before program code reaches production. A change that widens a permission is held for him by name. Page files and routine dependency updates go out behind automated checks alone. A repair agent runs three times a week. It can propose a fix and cannot merge one.
  • ControlsTests run on every change. After a site deploy a script opens the pages in a browser, and a failed check rolls the deploy back. Alarms watch what runs. Code checks AI text for numbers that are not in the data.
  • In publicEvery graded prediction is published, right or wrong. The cost figures on this page are read live. The code and the incident log are public.

What broke

Failures, and what changed.

Newest first. Each one opens to the cause, how it was found and what changed.

  • Oct 4
    The coaches’ new daily lines went live and showed none.

    The AI chose three coaches to speak and named each one. The code expected an internal id, refused all three, and the page said no coach had anything to say. The tests had passed. Found by a person reading the first live output, not by a monitor. Changed: the code accepts a name, and that live output is now a test case. The fix

  • Oct 3
    Two AI coaches gave opposite accounts of the same food log.

    One said logging had resumed. Another said it had been quiet for four days. A third cited an 11-day gap where the site showed 24. There was no single fact sheet for the day. Changed: the daily job was rebuilt so every coach reads one sheet, and code refuses a line that cites a value not on it. Its 14-day live proof is not finished. The issue

  • Sept 26
    A nutrient score reported a shortfall that was not there.

    The score counted food only and was published as total intake. It put one vitamin at 5% of its target on days the supplement record showed more than the full target, and the coaches were told to act on it. Changed: food, supplements and total are now three separate numbers. The issue

  • Sept 1
    The public ask-the-coaches feature returned errors for about 34 hours, across launch day.

    A quality check was given a 10-second limit, taken from a code comment that said it needed 2 to 5 seconds. Measured, its typical run was over 10. A monitor caught the failure the first morning. Nobody read that alarm for about 31 hours. Changed: the check was removed from the reader’s path. The incident log

  • Aug 26
    A feature passed its tests, was closed as done, and had never worked.

    It was meant to tell a harmless failed check from a real one. One network call returned a log with the needed line missing, and the feature fell back silently to the old behaviour. Found within the hour by using it on real work, not by an alarm. Changed: fixed the same day, and accepted only on a live result. The incident log

  • Aug 11
    The AI judge that blocks bad coach text passed invented numbers.

    Three test texts with made-up figures scored 92, 92 and 82 out of 100 and passed. The judge’s instructions had no rule about invented numbers. A separate check written in code did catch them, and none is known to have reached a reader. Found the first time the judge was measured against labelled examples. Changed: the blocking step now uses the code check’s verdict. The incident log

In his words

What I decided, and what I can’t verify myself.

Draft wording. Matthew has not rewritten this yet.

I decided what gets measured and what the goal is. I decided that the coaches’ predictions would be graded by code against a simple guess, and that the result would be printed when they lose. I set the monthly ceiling and chose what pauses first.

I did not write the code. An AI assistant wrote it at my direction, and I cannot tell by reading a change whether it is correct. On a long working session I let the assistant merge and deploy inside rules I set, and I see the result, not every line.

What I can check myself is whether a number about my own day is true, because I lived the day. For the rest I rely on the tests, the browser checks, the alarms and the published record of misses. When those fail, the failure goes in the list above.
