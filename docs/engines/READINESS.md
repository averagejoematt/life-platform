## Purpose

One 0–100 "how hard can I go today" composite. Two implementations exist **by design**:
the pre-compute model (daily, stored) and the live MCP tool model; the MCP tool cross-checks
itself against the stored value as a drift detector.

## Model 1 — pre-computed (the stored score)

`daily_metrics_compute_lambda.compute_readiness(data, baselines)` — runs daily before 11 AM PT,
stored on `USER#matthew#SOURCE#computed_metrics / DATE#<date>` as `readiness_score`,
`readiness_colour`, plus the component `breakdown` (#492/M-4: the actual inputs are stored
beside the score).

Components (weight re-normalizes over whichever are present):

| component | weight | score formula |
|---|---|---|
| Whoop recovery (today, else yesterday) | 0.40 | `recovery_score` used directly |
| Whoop sleep score | 0.25 | `sleep_score` used directly |
| HRV trend (7d avg / 30d avg) | 0.20 | `personal_baselines.readiness_hrv_score(ratio, baselines)` — piecewise linear through personal percentile anchors {p10→0, p50→50, p90→100}, clamped; fallback anchors {0.75, 1.0, 1.25} reproduce the legacy `clamp((ratio − 0.75) × 200)` exactly (#543/ADR-105 rule 4) |
| TSB (training form) | 0.10 | `clamp(round(60 + tsb × 2))` — TSB 0 → 60, −30 → 0, +20 → 100 |

```
score = round( Σ(vᵢ·wᵢ) / Σwᵢ )
colour: green ≥ 80 · yellow ≥ 60 · red < 60
```

Sleep is 25% (not 30%) deliberately, to stay aligned with the MCP model so the cross-check is a
true drift detector (comment at :448-451).

**TSB input:** Banister model in `lambdas/training/training_load.py` — CTL (42-day fitness), ATL (7-day
fatigue), `TSB = CTL − ATL`, over a 60-day Strava+Hevy window; loads are TSS-like points
(100 ≈ 1 h at threshold, #490). Per Strava activity, first match wins (#4075):

1. `kilojoules` present → `kJ / 7.2` (power-backed; basis `kj`).
2. `average_heartrate` present → **Banister TRIMP above the Zone-1 ceiling**: HRr =
   `(avg_hr − Z1) / (max_hr − Z1)` clamped to [0, 1], weighted `HRr·0.64·e^(1.92·HRr)`
   (Banister 1991; Morton, Fitz-Clarke & Banister 1990), normalised so 1 h at 165 bpm =
   100 (basis `hr`). `Z1` = 0.60 × the profile's measured max HR 183 = **109.8 bpm** — the
   zone-1 upper bound of the platform's one zone table (`mcp/helpers.HR_ZONE_BOUNDS`);
   the programme's walking cap (105 bpm, `owner_redlines`) sits under it. The ONE
   deviation from Banister, stated: HR reserve is measured above the Z1 ceiling instead of
   above resting HR, so recovery-intensity work contributes **0** to CTL/ATL.
3. no HR → duration proxy, labelled (basis `duration`): walks 25 points/h, anything else
   50 points/h.

Hevy is charged on **worked-set time** (#4075, owner ruling 2026-09-24, decision 4A) — not
the whole logged session, whose rest between sets, cardio block and stretching made the old
50 points/h × duration term 92–97 % of the window's load:

| Hevy set | charge | provenance |
|---|---|---|
| working rep set (`type` ≠ warmup) | `reps × 3.0 s` × 50 points/h | **assumed** — Hevy stores no per-set time on a rep set; 3.0 s/rep is the midpoint of ACSM 2009's moderate tempo (1–2 s concentric + 1–2 s eccentric; Ratamess et al., Med Sci Sports Exerc 41(3):687–708) |
| timed hold (duration, no distance) | `duration_sec` × 50 points/h | measured |
| cardio block (duration + distance) | `duration_sec` × the no-HR rate (walk pace ≤ 2.0 m/s → 25/h, else 50/h), **× the share of the session no HR-bearing Strava activity overlaps** | measured duration, proxy intensity |
| warm-up set, mobility (Stretching …) | 0 | — |
| workout with no set log | `duration_sec × 0.25` (`health.tdee.LIFTING_WORK_FRACTION_FALLBACK`) × 50/h | stated fraction |

**Which governs where both exist:** worked-set time governs LIFTING — a Strava copy of a Hevy
session (weight-training sport, or `device_name` "Hevy"; WHOOP records an HR-bearing one) is
skipped when Hevy has a record that day, because average HR over a lifting session is dominated
by rest and under-reads resistance work (Foster et al. 2001). HR governs a CARDIO block wherever
an HR-bearing Strava activity overlaps the session. No minute is counted twice. A Strava
weight-training activity with no HR and no Hevy record (the digests read Strava only) takes the
same 0.25 work fraction. The 50 points/h rate itself is unchanged (stated limitation: a set at
RPE 8 is harder per minute than IF 0.7, so the lifting term likely under-states).

The stored `tsb_load_basis` names the model (`model` = `trimp_above_z1_plus_hevy_worked_set_v2`;
`hr_model`, `lift_model`, `z1_ceiling_bpm`) and the provenance split (`confidence` ∈ power / hr /
worked_set / duration_proxy / mixed; `proxy_share` = duration-only share; `hr_share`;
`worked_set_share`; a `worked_set` block with the per-rep constant, its source, and assumed vs
measured seconds); every surface decides its "duration-proxy" label through
`training_load.is_duration_proxy` (≥ 50 % duration-derived).

| component | weight | formula |

`_precomputed_cross_check` against the stored `readiness_score`.

## Ambiguities (flagged, not resolved here)

- The two models use **different HRV maps** (personal bands vs fixed 60+200·(r−1)), **different
  TSB maps** (60+2·tsb vs 70+2.5·tsb) and **different traffic-light bands** (80/60 vs 70/40).
  The code comment claims the models are identical "on the typical day" (Garmin stale → Body
  Battery gated out), which holds for the weights but not for these sub-formula differences —
  the cross-check tolerance absorbs it. Documented as found.
- **One load model on the MCP side since #4075 decision 4A.** Model 2's `training_form` reads the
  STORED `tsb`; its fallback and `get_training view=load` (`mcp/tools_training._get_training_load`)
  now score each day with `training_load.daily_training_load` over Strava + Hevy — the retired
  `mcp/helpers.compute_daily_load_score` (raw kJ / un-normalised TRIMP / distance×10, blind to Hevy)
  is gone. **What still differs, stated:** view=load smooths with an EWMA warm-started over an
  84-day warm-up, the stored TSB with a cold-started 60-day window, so the two TSBs can differ by
  the seed's residual (never by the load model). view=load's per-row `acwr` is the Banister ATL/CTL
  ratio; `view=recommendation`'s RED injury override now reads the platform's ONE ACWR,
  `computed_metrics.acwr` (acwr-compute, Whoop-strain EWMA 7/28) — on 2026-09-15..22 the Banister
  ratio read 2.5–2.8 (a new programme over a low summer base) while acwr-compute read 1.28 "safe".
