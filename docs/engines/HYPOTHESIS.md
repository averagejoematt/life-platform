## Purpose

Weekly (Sunday 11 AM PT) cross-domain hypothesis loop: an LLM proposes hypotheses **with a
frozen machine-checkable test spec** (the pre-registration); pure Python decides every verdict;
every resolution writes a calibration-ledger row. ADR-105 rule 3: deterministic before narrative
— no LLM ever sees the data at check time.

## Inputs

30 days of multi-source data (`whoop, garmin, macrofactor, apple_health, withings, strava,
notion, habitify, eightsleep`) flattened to day-rows by `build_data_narrative` (:382-492).
Checks see the full 30 days (`LOOKBACK_DAYS`); generation sees the last 14 (`GENERATION_DAYS`).
Generation requires ≥10 days with ≥5 non-null metrics (`MIN_DATA_DAYS`, `MIN_METRICS_PER_DAY`).

## The pre-registered test spec (#530)

At creation the LLM must emit a `test_spec`, validated deterministically and **frozen** —
hypotheses without a parseable spec are rejected (`validate_test_spec`, :594-641). Since #4276 the generation
reply is also constrained at the model by `HYPOTHESES_SCHEMA` (`lambdas/compute/compute_json_schemas.py`: the
metric slots are `SPEC_METRICS` enums), but the deterministic validators below remain the authority:

- `condition_metric`, `outcome_metric` — both from the fixed `SPEC_METRICS` vocabulary
  (:162-200, exactly what `build_data_narrative` emits — a spec can only reference values the
  check path can compute), and must differ.
- `condition_op` ∈ {`>=`, `<=`, `median_split`} (+ numeric `condition_threshold` for the first two)
- `direction` ∈ {higher, lower}; `min_effect ≥ 0` (outcome units); `lag_days` 0–3.
- **The bar is derived at the write (#3495, ADR-105 rule 4).** `store_hypothesis` → `prereg_effect.stamp_spec_provenance` replaces the model's (or a design-declared) `min_effect` with 0.5 × the mean-successive-difference SD of the outcome metric's own trailing series (the full 30-day `daily_rows`, n ≥ 5 successive readings), stores `min_effect_basis` `{metric, unit, window_days, statistic, value, k, n, n_floor, replaced}` beside it, and rewrites `confirmation_criteria` from that number (the model's sentence is kept as `proposed_confirmation_criteria`). Too short or flat a series keeps the declared bar, labelled `model_proposed`/`population_constant`. `experiment_gates.min_effect_meets_rigor_bar(spec)` recomputes the bar from its basis — a derived bar meets ADR-105's bar, a labelled or hand-typed one does not. Records frozen before #3495 are never re-priced.

Other creation gates (`validate_hypothesis`, :506-558): required fields incl. confidence ∈
{low, medium, high}; ≥2 domains; a numeric threshold with units in `confirmation_criteria`;
`monitoring_window_days` 7–30; >50% word-overlap duplicate rejection. Caps: ≤5 new per run
(`MAX_NEW_HYPOTHESES`), ≤20 pending (`MAX_PENDING_HYPOTHESES`).

## The deterministic check (`evaluate_test_spec`, :644-747)

Pure Python, weekly, per pending/confirming hypothesis that is ≥7 days old
(`MIN_SAMPLE_DAYS_FOR_CHECK`):

1. Pair each day's condition value with the outcome value at `lag_days` offset.
2. Split into condition vs comparison arms (threshold, or median split with strictly-above).
3. Require ≥5 days per arm (`MIN_DAYS_PER_ARM`) and ≥10 pairs total; else inconclusive.
4. `effect = mean(condition) − mean(comparison)`; moving-block-bootstrap 95% CI
   (`stats_core.bootstrap_mean_diff_ci`) + Cohen's d.

```
supported     — CI excludes 0 in the predicted direction AND |effect| ≥ min_effect
contradicted  — CI excludes 0 in the OPPOSITE direction
inconclusive  — arms too thin or CI straddles 0
```

## Watch-enabled pre-registrations (#4979)

`lambdas/compute/watch_hypotheses.py` registers three hypotheses in code, written 2026-10-24 before
the Apple Watch data that grades them is read — the #1843 diary seed's contract: fixed ids, idempotent
across every status, validated by `validate_hypothesis`, frozen by `store_hypothesis` (whose
`pre_registered_at` is the check's `since_date`), bar labelled `population_constant` with
`WATCH_DESIGN_CITATION` unless re-derived from the outcome's trailing variance (#3495):

- `hyp_watch_daylight_sleep_onset` — `daylight_min` median split → `sleep_onset_min` lower, lag 1 (sleep rows are keyed by wake date), bar 3 min.
- `hyp_watch_zone2_cardio_recovery` — `zone2_7d_min` (THE Zone 2 computation, Apple's own zones as its third source) median split → `cardio_recovery` higher, lag 0, bar 2 bpm; **`public: False`** (cardio recovery is TIER_INTERNAL).
- `hyp_watch_training_vo2max` — `cardio_7d_min` median split → `vo2max` (through the VO2 resolver) higher, lag 1, bar 0.5 ml/kg/min.

Each states its decision rule (`decision_rule`) and design date (`design_registered_on`) on the record; a
hypothesis whose arms never fill expires undecided at the 30-day hard limit.

## Lifecycle (status machine, in `check_pending_hypotheses`, :1147-1222)

```
pending ── supported (window open) ──▶ confirming
pending/confirming ── supported AND days_old ≥ monitoring_window ──▶ confirmed   (resolution)
pending/confirming ── contradicted ──▶ refuted                                   (resolution)
pending/confirming ── window expired, no verdict ──▶ archived / expired_undecided (resolution)
anything non-terminal older than 30 days ──▶ archived (hard expiry, `enforce_hard_expiry`, :561-585)
```

v1 legacy hypotheses (no `test_spec`) are never checked — they age out via hard expiry.
On resolution, Haiku **narrates** the already-decided verdict (one sentence, only numbers from
the deterministic evidence string; fail-soft to the deterministic sentence — `narrate_resolution`,
:816-883).
